# ADR 0010 — MCTS（UCT）はプレイアウト数で打ち切り、Core は同じ `apply` の経路のまま速くし、キャスト 4 名は探索の設定で性格を分ける

- 状態: 受理（キャストの名前と性格は施主に知らせる・REQUIREMENTS の Q7）
- 日付: 2026-10-26
- Issue: #9
- 影響する規則: ARC-001 / ARC-003 / ARC-007 / SWF-012 / FR-03 / FR-05 / FR-06 / FR-14

## 文脈

FR-03: AI は MCTS（UCT）＋ランダムプレイアウト。探索は時間ではなくプレイアウト数で打ち切り、Core と Engine は時計を知らない。
並行性は使わない（SWF-013）ので、1 手の探索が 1 手の間隔（1.0 秒・FR-11）に収まる量を計測して決める（WORK-ORDER 第 2 節）。
Engine のプレイアウトは Core の合法判定を通る（第 2 の合法判定を作らない・速くしたいなら Core を速くする）。

**最初に測ったプレイアウトの速さ**（2026-10-26・WSL2・release・19 路・自分の眼を埋めない乱数）: ADR 0005 の Core では毎秒約 47 局（1 局約 21 ミリ秒）。
1 手 1 秒では 50 回しかプレイアウトできず、MCTS にならない。遅い原因は、1 手ごとに `moves + [move]` と `seenBoards.union` で配列と集合を丸ごと複製し（1 局で手数の 2 乗）、
塗りつぶしのたびに印の配列と隣の配列を確保し、候補を作るたびに 361 点の配列と眼の判定の配列を確保していたこと。

## 決定

### Core を速くする（経路は 1 つのまま）

1. **打つ経路は `Position.apply(_:)`（内部）と `Game.apply(_:)`（公開・`mutating`）の 1 つずつ**。`Position.play`・`Game.play` は写しに `apply` で打って新しい値を返すだけ。
   拒んだときは局を変えない（自殺手は置いた石を戻す。局面スーパーコウは局面の写しで判定してから入れ替える）。プレイアウトは手元の写しを `apply` で進める
2. 塗りつぶしの印と積み上げは 420（19 路の番兵つきの配列の長さ）の `InlineArray` に置き、ヒープを確保しない。隣は `BoardSize.neighbor(of:_:)` で配列を作らずに回す
3. 空点の一覧は `Position.emptyPoints()` が 1 回の走査で作る。眼の判定（`EyeShape`）は配列を作らない
4. 結果: 同じ条件で **毎秒約 1,560 局（19 路・1,000 局で 0.64 秒）・9 路は毎秒約 9,300 局**。約 33 倍。ルールのテスト（Tromp の合法局面数・手作りの局面・不変条件）は変えずに全部通った

### MCTS（`MonteCarloSearch`）

5. 木は配列の節（`TreeNode`）で、親と子を位置で指す。根の候補は手番の側の眼でない空点を乱数の順に並べたもの（無ければパスだけ）。
   選択は UCT（勝率＋係数 × √(ln 親の訪問 / 子の訪問)）、展開はまだ試していない手を 1 つ `Game.apply` で打ち（打てなければ捨てて次）、
   プレイアウトは `Playout.run`（自分の眼を埋めない乱数・手の好みつき）で終局まで打ち、勝った側を数えて根まで戻す
6. 打つ手は訪問のいちばん多い子。**序盤のばらつき（FR-05）**: 局の始めの数手（性格ごと）は、訪問の上位 3 手から訪問の数に比例した乱数で選ぶ。
   根の候補の並びが乱数なので、同じ訪問の数の手も乱数で決まる
7. 打てる意味のある手（眼でない空点）が無ければパスする。両者がパスすれば終局する（投了は入れない・REQUIREMENTS）
8. ln と平方根は Engine の中で自前で求める（`NaturalLog`・`SquareRoot`）。🔴 `Double.squareRoot()` は release 構成で libm の `sqrt` を呼び、
   Glibc を import しない実行ファイル（計測用の小さなパッケージ）でリンクできなかった（`undefined reference to 'sqrt'`・2026-10-26 の実測）。
   Engine は標準モジュールを import しない（ARC-003）ので、テストの実行ファイルでも同じことが起きうる

### キャスト 4 名（REQUIREMENTS の Q7・FR-06）

| 名前 | 性格 | プレイアウト | 探索の係数 | 手の好み | 序盤の手数 |
| --- | --- | --- | --- | --- | --- |
| `SENTE.SYS` | 先手を取りたがる。直前の手に接触して打ち合う | 550 | 0.9 | `contact`（半分の確率で直前の手の周り 8 点から試す） | 4 |
| `TENUKI.LOG` | すぐ手を抜く。好みなく散らかす。序盤が長く荒れる | 650 | 1.0 | `scatter`（好みなし） | 10 |
| `MOYO.PNG` | 模様を張りたがる。中央を好む | 600 | 1.1 | `centerSeeking`（1 線の点を半分の確率で選び直す） | 6 |
| `SEKI.LCK` | 動かない。知っている手に固執する（探索の項が小さい） | 450 | 0.6 | `contact` | 2 |

Gambit（VEX.EXE / MORT.SH / NULL_PTR / GRANNY.DLL）・Reversi（FLIP.BAT / CORNER.SYS / SPAM.EML / LAZY.CRON）と違う名前で、`ファイル名.拡張子` の作法をそろえた。
囲碁の用語（先手・手抜き・模様・セキ）を名前にした。局ごとに 4 名から違う 2 名を乱数で選び、乱数で黒白に分ける（`Players.drawn`）。顔とセリフは手順 5。

### 計測（2026-10-26・WSL2・release・19 路・コミ 7.5・最終の設定）

12 の黒白の組み合わせ × 種 3 つ = **36 局**（12 局を並列に走らせたので、1 手の時間は単独より長めに出る）:

| 項目 | 値 |
| --- | --- |
| 1 局の手数 | 最小 391・中央 436.5・最大 525・平均 444 |
| 1 局の探索の合計時間（並列） | 最小 129 秒・中央 189 秒・最大 234 秒 |
| 1 手の探索の時間（並列） | 平均 414 ミリ秒・最大 866 ミリ秒（序盤 10 手の平均の最大 836 ミリ秒） |
| 1 手の探索の時間（2 局だけ並列） | 平均 266〜280 ミリ秒・最大 521〜540 ミリ秒 |
| 黒の勝ち | 36 局中 20 |
| 各キャストの勝ち（18 局ずつ） | SENTE.SYS 8・TENUKI.LOG 9・MOYO.PNG 7・SEKI.LCK 12 |
| 勝った側から見た差 | 最小 0.5 目・中央 25.5 目・最大 103.5 目（10 目未満 9 局・50 目超 10 局） |
| アゲハマの合計（中央） | 121 個 |

最初の設定（SENTE 700・TENUKI 350 で係数 1.4・MOYO 600・SEKI 900）では SEKI.LCK が 18 局中 17 勝・TENUKI.LOG が 2 勝で、勝敗がばらつかなかった。
プレイアウトの数を寄せ（SEKI 450・SENTE 550）、TENUKI を 650・係数 1.0 に変えて上の表になった（TENUKI の 18 局は変えた後に測り直した）。
1 手の探索はどの局面でも 1.0 秒の間隔に収まった（並列でも最大 866 ミリ秒）。

**1 局の長さ**: 1 手 1.0 秒（FR-11 の初期値）で約 444 手なので、**1 局は約 7.4 分**（探索は間隔の中で行う。間隔より長くかかった手は、その分だけ次の手が遅れる）。
投了は入れていない。終盤は駄目を詰め、自分の眼だけが残るまで打つ。

## 強制

- **active**（テスト・`make check` の `test` 段）: 9 路で 100 プレイアウトの MCTS が乱数の打ち手に 10 局中 9 局以上勝つ・返す手は Core が打てると言う手で、同じ乱数の種からは同じ手・
  眼しか無ければパス・ln と平方根の精度・キャストの 4 名の名前が違い、組む 2 名が違う・同じシードからは同じ対局の列
- **planned**: 1 手の探索が 1.0 秒に収まることは、この ADR の計測だけ（機械は時間を見ない。遅い計算機では間隔より長くなる）

## 結果

- 画面の HUD に黒白のキャストの名前を出す（FR-10）
- 🔴 プレイアウトが自分の眼を埋めない乱数なので、強さは弱い（死活を読まない）。スクリーンセーバーとして「打ち合いが見える」ことを狙った
- 🔴 序盤の数手は上位 3 手から選ぶので、悪い手も混ざる（ばらつきの代わり）
- 🔴 1 局が約 7.4 分と長い。投了の要否は施主に数字を添えて聞く（REQUIREMENTS の「施主に聞いてから決めること」）

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| プレイアウトの中だけで使う速い合法判定（自殺手とスーパーコウを省く） | 第 2 の合法判定になる（ARC-001・WORK-ORDER 第 2-1 節）。Core を速くした |
| 時間で探索を打ち切る | Core と Engine が時計を知ることになる（ARC-007）。同じシードから同じ対局にならない |
| 探索を別のスレッドで回す | 並行の形が 2 つになる（SWF-013） |
| 木の節をクラスで持つ | 値型の配列で足りる。公開しないので SWF-018 にもかからないが、参照の共有が要らない |
| RAVE / AMAF・パターンのプレイアウト | 強さは要件でない。まず計測できる形を入れた。要るなら別の ADR |
| `Double.squareRoot()` を使う | libm の `sqrt` にリンクする（上の実測） |
| 最初の設定のまま | 1 名が 18 局中 17 勝で、勝敗のばらつき（FR-06）が無かった |
