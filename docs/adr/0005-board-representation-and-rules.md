# ADR 0005 — 盤は番兵つきの 1 次元配列、手は「点に打つ／パス」の閉じた enum、局面スーパーコウは盤の配置の Zobrist ハッシュで見る

- 状態: 受理
- 日付: 2026-10-26
- Issue: #3
- 影響する規則: ARC-001 / ARC-004 / ARC-005 / ARC-008 / ARC-010 / SWF-001 / SWF-002 / SWF-004 / SWF-005 / SWF-007

## 文脈

盤の表現・手の内部表記・パスの表し方・局面の文字列表現は、それぞれ 1 つに決めて ADR に書く必要がある（PROJECT_LAYOUT 第 3 節・用語集）。
「合法か」「終局したか」「何目差か」を判定する経路は Core に 1 つずつでなければならない（ARC-001・ARC-004）。Engine のプレイアウトもこの経路を通る。

材料:

- 製品は 19 路だけを使うが、Core は盤の大きさを引数で持ってよい（REQUIREMENTS の Q4）。正しさは小さい盤の合法局面数で確かめる（ADR 0006）。
  Tromp の公表値は正方形の盤だけでなく m×n の表もある（1×n〜4×n）ので、長方形の盤を扱えると、数え上げられる大きさの例が 4 つから 19 に増える
- 兄弟の Reversi は盤を 64 ビット 2 枚にした（Reversi ADR 0005）。19 路の 361 点は 64 ビットに収まらず、ビット演算の盤は 6 語の配列になる
- `UInt64` の `*` は `-O` でも桁あふれで落ちる（ADR 0001 の X-g）。`&*` は 2^64 の余りになる（X-h）

## 決定

1. **盤は `Position` の中の番兵つきの 1 次元配列 `cells: [BoardCell]` だけ**。行の幅は `width + 1` で、各行の先頭のマスと上下の 1 行が番兵 `offBoard`。
   点 `(x, y)` の位置は `(y + 1) * (width + 1) + x + 1`、縦横の隣は `±1` と `±(width + 1)`。`x` は左から、`y` は下から 0 始まり。
   `BoardCell` は Core の中だけの型で、外へは `PointState`（空・黒・白の閉じた enum）で見せる
2. **盤の大きさ `BoardSize` は 1〜19 の幅と高さ**（唯一のファクトリ `BoardSize.make`）。製品の 19 路は `BoardSize.nineteen`。
   長方形はテストで Tromp の m×n の表と突き合わせるために持つ。13 路・9 路の切り替えのような製品の機能ではない（施主が言っていない）
3. **手は `Move` の 1 表記**: `.place(Point)` か `.pass`。点 `Point` は 0〜18 の列と行で、どの盤の中にあるかは `BoardSize.contains` が決める。
   表示（列 `A`〜`T` で `I` を飛ばす・行 1〜19）は Render が持つ
4. **連は持たない**。呼吸点と取りは、打った点の縦横から塗りつぶしで求める（呼吸点が見つかったら止める）。打つ手順は
   「空点か → 石を置く → 隣の相手の連のうち呼吸点の無いものを全部取る → 何も取らずに自分の連の呼吸点が 0 なら自殺手として拒む」。
   盤の上だけで決まる拒否（盤の外・占有・自殺手）は `Position.play` が `PlacementRejection` で返す
5. **局面スーパーコウは `Game` が見る**: 打った後の盤上の石の配置（手番を含まない）が、この局で前に現れた配置（始めの盤を含む）と同じなら `.superko` で拒む。
   配置の同一は **64 ビットの Zobrist ハッシュの一致**で判定し、ハッシュは石を置く・取るたびに差分で更新する。鍵は固定の種からの SplitMix64 の定数（`&+`・`&*`）。
   パスは盤を変えないので配置を増やさず、常に打てる（終局後を除く）
6. **終局は連続 2 回のパス**（`Game.status`）。勝敗は `AreaScore.counting`（盤上の石＋その色だけに接する空点の領域）とコミ（`Komi`・半目の数で持ち、
   正の奇数だけを受け付けるので引き分けは起きない）で `GameResult` が決める。死に石の判定はしない（FR-04）
7. **局面の文字列表現は「盤・空白 1 つ・手番」**。盤は上の行から `/` で区切り、各行は左から黒 `X`・白 `O`・空点 `.`、手番は `X` か `O`。
   例: 3 路の空の盤は `.../.../... X`。行の数と長さが盤の大きさになる。読み書きは `PositionCodec` の 1 経路だけで、
   読めない文字列は `PositionDecodeRejection` の理由で返す。呼吸点の無い連がある盤は読まない（`Position.make` が拒む）
8. **手を打つと新しい値を返す**（`Position.play` も `Game.play` も元の値を変えない）

## 強制

- **planned**（ARC-001）: 盤の表現と手の表記を混ぜないことは、型が 1 つしか無いことで成り立つが、2 つ目を作らないことはレビュー事項
- 正しさ: ADR 0006 のテスト（合法局面数・着手でたどり着ける配置の数・手作りの局面・不変条件）が `make check` の `test` 段で回る

## 結果

- 盤の大きさを変えても同じコードが動くので、19 路の製品の盤と、テストの小さい盤が同じ経路を通る
- 🔴 **Zobrist ハッシュの衝突は検出しない**。違う配置が同じハッシュになると、合法な手を `.superko` で拒む。1 局の配置の数を 1,000 として、
  ある手が偶然いずれかと衝突する確率はおよそ 1,000 / 2^64（約 5×10^-17）で、スクリーンセーバーでは無視する。正しさのテストは差分更新と全計算の一致だけを見る
- 🔴 速さは測っていない。1 手ごとに配列を複製し、塗りつぶしのたびに印の配列を作る。`Game` は打つたびに配置の集合を複製する。
  MCTS のプレイアウトの速さが足りなければ、Phase 3-4 で測ってから Core を速くする（第 2 の合法判定は作らない）
- 実装中に、合法局面数のテストが `Position.make` の欠陥を見つけた（ADR 0006 の「結果」）

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| 361 ビットのビット盤（`UInt64` 6 語）を黒白 2 組 | 隣の点へのずらしが語をまたぎ、行の回り込みのマスクも要る。取りと呼吸点の塗りつぶしは配列のほうが素直で、速さが足りないと分かってから考える |
| 連（石の集合と呼吸点の数）を盤と一緒に持って差分で更新する | 速いが、連の合流と分割の更新は誤りやすい。まず塗りつぶしで正しさを公表値と合わせ、速さが要るなら測ってから ADR で変える |
| 点を 1 次元の位置（`Int`）のまま公開する | 番兵の位置と盤の大きさに依存する値が Core の外に漏れる（SWF-001） |
| 単純なコウ（直前の配置だけ）を見る | 施主の決定は局面スーパーコウ（FR-02）。単純なコウでは止まらない循環がある（KoTests の 2 つのコウの例） |
| 配置の履歴を盤ごと持ち、ハッシュが一致したら盤を比べる | 衝突も検出できるが、1 局の記憶が盤の数だけ増え、プレイアウトの複製も重くなる。上の衝突の確率の見積もりで足りると判断した |
| 状況スーパーコウ（手番も含めて同一を見る） | 施主の決定は局面スーパーコウ（盤上の配置だけ） |
| 盤の大きさを正方形だけにする | 数え上げで確かめられる Tromp の値が 1〜4 路の 4 つに減る |
| 局面の文字列表現に SGF を使う | SGF は棋譜の形式で、局面の 1 行の表現ではない。テストの手作りの局面は盤の絵のまま読めるほうが確かめやすい |
